## 🧱 Assign and Expand Values

An assignment has no spaces around `=` and does not put `$` before the variable name. Use `$name` or `${name}` to read its value:

```bash
app_name='orders-api'
release_version='1.4.0'
printf 'App: %s\nVersion: %s\n' "$app_name" "$release_version"
```

Output:

```text
App: orders-api
Version: 1.4.0
```

Braces make the variable boundary clear when more characters follow it:

```bash
region='eu-west'
printf '%s\n' "${region}-staging"
```

Without braces, `$region-staging` means the value of `region` followed by `-staging`, too; braces make the boundary easier to read and safer when adjacent characters could be part of the name.

## 🔐 Quote Values Passed to Commands

Double quotes allow expansion while preserving the expanded value as a single argument. This matters when a path or application name contains spaces:

```bash
artifact_dir='/srv/build output'
printf 'Artifact directory: %s\n' "$artifact_dir"
```

Unquoted expansions can undergo word splitting and wildcard expansion. Prefer `"$artifact_dir"` when passing a variable as an argument. ShellCheck flags many accidental cases as [SC2086](https://www.shellcheck.net/wiki/SC2086).

| Form | What happens | Common use |
|---|---|---|
| `'text $name'` | Keeps `$name` literal. | Fixed text or a quoted here-document. |
| `"$name"` | Expands the value and keeps it one argument. | Passing a value to a command. |
| `\$` | Escapes a dollar sign in an unquoted context. | Literal special characters. |

Single quotes prevent variable expansion; double quotes allow it:

```bash
deploy_env='staging'
printf 'Literal: %s\n' '$deploy_env'
printf 'Expanded: %s\n' "$deploy_env"
```

Expected output:

```text
Literal: $deploy_env
Expanded: staging
```

See the Bash manual’s [Quoting](https://www.gnu.org/software/bash/manual/html_node/Quoting.html) section for the complete rules.

## ⚙️ Use Deployment Configuration

Environment variables pass configuration into child processes, which makes them useful in CI jobs and service launchers. A script can read a value, choose a safe default, and fail with a clear message when a required setting is missing:

```bash
#!/usr/bin/env bash

app_name=${APP_NAME:?Set APP_NAME before running this script}
deploy_env=${DEPLOY_ENV:-staging}
release_tag=${RELEASE_TAG:-unreleased}

printf 'App: %s\nEnvironment: %s\nRelease: %s\n' \\
    "$app_name" "$deploy_env" "$release_tag"
```

- `${NAME:-default}` uses the default when `NAME` is unset or empty.
- `${NAME:?message}` stops with a message when the value is unset or empty.
- Lowercase names are commonly used for script-local variables; uppercase names are conventional for environment settings.

Run it with values for just this invocation:

```bash
APP_NAME='market api' DEPLOY_ENV='test' RELEASE_TAG='v1.4.0' bash release-report.sh
```

Because `APP_NAME` is quoted in the script, `market api` stays together as one value.

To make a value available to later child processes in the current shell, export it:

```bash
export APP_ENV='staging'
bash -c 'printf "Child sees: %s\\n" "$APP_ENV"'
```

The `NAME=value command` form sets a value for that command’s environment only; it does not change the parent shell’s variable.

## 📥 Capture Command Output

Command substitution stores a command’s standard output in a variable. For example, a deployment report can show the Git revision being built:

```bash
commit_id=$(git rev-parse --short HEAD)
printf 'Building commit %s\n' "$commit_id"
```

This needs to run inside a Git repository. Bash removes trailing newline characters from command-substitution output. Prefer `$(...)` to legacy backticks because it is easier to read and can be nested.

Pipelines can prepare text before a script stores or reports it:

```bash
printf '%s\n' "$PATH" | tr ':' '\n' | sort -u
```

This prints unique `PATH` entries in sorted order. Each command receives the previous command’s standard output through standard input.

### 🧪 Interview Q&A

**Q1:** What is wrong with `release_tag = 'v1.4.0'` as an assignment?

**Q2:** Why should a path variable usually be written as `"$path"` when passed to a command?

**Q3:** What is the difference between a shell variable and an exported variable?

**Q4:** What does `${DEPLOY_ENV:-staging}` do?

**Q5:** When would you use command substitution?

> [!answer]- 📋 Answers
>
> **A1:** Spaces split it into command words; write `release_tag='v1.4.0'`.
>
> **A2:** Quoting preserves the value as one argument and prevents word splitting and wildcard expansion.
>
> **A3:** Child processes inherit an exported variable; an unexported shell variable remains local to that shell.
>
> **A4:** It expands to `DEPLOY_ENV` when non-empty, otherwise to `staging`.
>
> **A5:** When a script needs to store a command’s output for a later command or message.

### 🔨 Hands-On Tasks

#### Task 1: Preserve a Value with Spaces

**Goal:** See how quoting keeps a multiword value together.

**Commands:** Save the configuration example above as `release-report.sh`, then run:


**Steps:** Check that the script uses `"$app_name"`, then run it with the one-command environment assignment.

#### Task 2: Compare Exported and One-Command Values

**Goal:** Observe which values a child Bash process receives.

**Commands:**

```bash
export APP_ENV='staging'
bash -c 'printf "Child sees: %s\\n" "$APP_ENV"'
APP_ENV='production' bash -c 'printf "One run: %s\\n" "$APP_ENV"'
printf 'Parent still sees: %s\n' "$APP_ENV"
```

**Steps:** Run the commands in one shell and compare the child process output with the parent’s final value.

**Done when:** The child sees `staging`, the one-command run sees `production`, and the parent still sees `staging`.

### 📋 Quick Reference

| Need | Syntax |
|---|---|
| Assign a value | `name=value` |
| Expand as one argument | `"$name"` |
| Make the name boundary explicit | `${name}` |
| Use an optional default | `${NAME:-default}` |
| Require a value | `${NAME:?message}` |
| Capture command output | `value=$(command)` |
| Export to child processes | `export NAME=value` |
| Set a value for one command | `NAME=value command` |

### 🧠 Things to Remember

- Bash assignments have no spaces around `=`.
- Quote expansions when they are command arguments.
- Exported values cross process boundaries; ordinary shell variables do not.
- Never print secrets just to confirm they are set.

### 💡 Pro Tips

- Set safe defaults for optional configuration and fail clearly for required values.
- Use `$(...)` for readable command substitution.
- Print the name or presence of a secret when debugging, never its value.
- Run ShellCheck to catch common quoting mistakes.
