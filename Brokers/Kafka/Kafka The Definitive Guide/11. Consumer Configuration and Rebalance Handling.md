The settings that shape how much a consumer fetches, how fast a dead one is noticed, where a new group starts, and how partitions are shared, plus the hooks for rebalances, seeking, clean shutdown, and consumers without a group.

---

## 📥 Fetch Settings

| Kafka property | Default | Effect |
|---|---|---|
| `fetch.min.bytes` | 1 byte | Broker waits until it has at least this much data. Raise it to cut requests on quiet topics |
| `fetch.max.wait.ms` | 500 ms (franz-go: 5 s) | …but never longer than this |
| `fetch.max.bytes` | 50 MiB | Max data per fetch across partitions; the main memory limit |
| `max.partition.fetch.bytes` | 1 MiB | Max per partition; harder to reason about, prefer `fetch.max.bytes` |
| `max.poll.records` | 500 | Records per poll (Java); in franz-go, `client.PollRecords(ctx, 500)` |

> 🧮 **Example:** `fetch.min.bytes`=1 MB and `fetch.max.wait.ms`=100 ms → the broker answers when it has 1 MB **or** after 100 ms, whichever comes first.

A first batch bigger than the byte limits is still returned, so a consumer can't get stuck on one large record.

## 💓 Liveness and Timeouts

| Kafka property | Default | Purpose |
|---|---|---|
| `session.timeout.ms` | 45 s | No heartbeat for this long → member declared dead → rebalance |
| `heartbeat.interval.ms` | 3 s | How often to heartbeat; keep it about **⅓** of the session timeout |
| `max.poll.interval.ms` | 5 min (Java) | Max gap between polls before a Java consumer leaves the group |
| `rebalance.timeout.ms` | 60 s (franz-go) | Time members get to finish work and rejoin once a rebalance starts |
| `request.timeout.ms` | 30 s | Wait for a broker reply before reconnecting; don't lower it |
| `default.api.timeout.ms` | 60 s | Default for Java API calls without an explicit timeout |

- ⚖️ **Shorter session timeout** → failures detected sooner, but GC pauses or slow networks cause needless rebalances. **Longer** → fewer false alarms, slower recovery.

- 🧟 **Why a separate poll limit?** Heartbeats run in the background, so a consumer whose main loop is deadlocked would still look alive. The poll interval (Java) or rebalance timeout (franz-go) catches that.

> 🆕 **Current Kafka:** the book gives 10 s for `session.timeout.ms`; since Kafka 3.0 the default is 45 s.

## 🏁 Where a New Group Starts

**`auto.offset.reset`** applies when a group has **no committed offset** for a partition, or the committed one **no longer exists** (it aged out of retention).

| Value | Starts at | Risk |
|---|---|---|
| `latest` (Java default) | Only records written from now on | Earlier records are skipped |
| `earliest` | The oldest record still kept | Reprocesses everything retained |
| `none` | Throws an error | You decide in code |

> ⚠️ **franz-go's defaults differ:** a group with no commits starts at the **earliest** offset (`kgo.ConsumeStartOffset`), and a committed offset that fell out of retention rewinds to about one minute before the end (`kgo.ConsumeResetOffset`). The project sets `ConsumeResetOffset(AtStart())` explicitly, so a new Shipping deployment processes every `OrderPaid` still in the topic.

## 🧩 Partition Assignment Strategies

Two consumers, C1 and C2, both read topics T1 and T2, each with 3 partitions:

| Strategy | C1 gets | C2 gets | Notes |
|---|---|---|---|
| **Range** | T1: 0, 1 · T2: 0, 1 | T1: 2 · T2: 2 | Per topic, consecutive; uneven when counts don't divide |
| **RoundRobin** | T1: 0, 2 · T2: 1 | T1: 1 · T2: 0, 2 | All partitions dealt out one by one; balanced |
| **Sticky** | Balanced like RoundRobin | | Keeps assignments in place on rebalance |
| **CooperativeSticky** | Same as Sticky | | Plus cooperative (incremental) rebalancing |

- ☕ **Java default:** `[RangeAssignor, CooperativeStickyAssignor]` (Range first, upgradeable to cooperative).

- 🐹 **franz-go default:** cooperative-sticky, set with `kgo.Balancers(...)`.

## 🏢 Fetching from the Closest Replica

By default consumers read from each partition's **leader**. In a cluster spread across availability zones, reading from a replica **in your own zone** is faster and avoids cross-zone network fees.

- 🖥️ Brokers: `replica.selector.class=org.apache.kafka.common.replica.RackAwareReplicaSelector`

- 💻 Consumers: `client.rack` = your zone → `kgo.Rack("eu-west-1a")`

## 🔔 Rebalance Callbacks

Hooks run when a consumer gains or loses partitions (Java's `ConsumerRebalanceListener`):

| Java | franz-go | Use it to |
|---|---|---|
| `onPartitionsAssigned` | `kgo.OnPartitionsAssigned(fn)` | Load state, seek, warm caches for new partitions |
| `onPartitionsRevoked` | `kgo.OnPartitionsRevoked(fn)` | **Commit** finished work before others take over; close resources |
| `onPartitionsLost` | `kgo.OnPartitionsLost(fn)` | Partitions were taken without a clean revoke; **don't** commit them |

```go
kgo.OnPartitionsRevoked(func(ctx context.Context, cl *kgo.Client, _ map[string][]int32) {
    // Commit synchronously, so the next owner starts after our last processed record.
    if err := cl.CommitUncommittedOffsets(ctx); err != nil {
        slog.Error("commit on revoke failed", "error", err)
    }
})
```

With cooperative rebalancing, `revoked` is called only with the partitions actually moving. The project avoids callbacks entirely with `kgo.BlockRebalanceOnPoll()`: no rebalance can happen between a poll and its commit, so there's nothing to commit on revoke.

## ⏩ Seeking to an Offset

Sometimes you want to start somewhere other than the committed offset: replay from the beginning, skip to the end, or rewind to a point in time.

| Java | franz-go |
|---|---|
| `seekToBeginning` | `kgo.ConsumeResetOffset(kgo.NewOffset().AtStart())` for new groups, or `client.SetOffsets(...)` |
| `seekToEnd` | `kgo.NewOffset().AtEnd()` |
| `offsetsForTimes` + `seek` | `kgo.NewOffset().AfterMilli(ms)`, or `kadm.Client.ListOffsetsAfterMilli` + `SetOffsets` |

For an existing group, the simplest tool is `kafka-consumer-groups.sh --reset-offsets` while the group is stopped (lesson 12).

## 🚪 Shutting Down Cleanly

Java calls `consumer.wakeup()` from a shutdown hook to break a long `poll()`, then `close()`. In Go, **cancel the context**: `PollFetches(ctx)` returns, the loop exits, and `Close()` **leaves the group** so partitions move immediately instead of after the session timeout.

```go
// shipping/cmd/main.go
ctx, stop := signal.NotifyContext(context.Background(), os.Interrupt, syscall.SIGTERM)
defer stop()
// ...
workers.Go(func() { consumer.Run(ctx) }) // returns when ctx is cancelled
// ... after the gRPC server stops:
workers.Wait()
consumer.Close() // LeaveGroup: partitions move at once
```

## 🧍 Consumers Without a Group

A **standalone consumer** assigns itself partitions instead of joining a group: no rebalances, no shared work. Use it when one process must read **all** partitions (or specific ones) and nothing else should share them.

```go
// tools/eventtail/main.go: reads everything, joins no group, commits nothing
client, err := kgo.NewClient(
    kgo.SeedBrokers(brokers...),
    kgo.ConsumeTopics(*topic),
    kgo.ConsumeResetOffset(kgo.NewOffset().AtStart()),
)
// or exact partitions:
// kgo.ConsumePartitions(map[string]map[int32]kgo.Offset{"orders": {0: kgo.NewOffset().AtStart()}})
```

A consumer either subscribes (group) **or** assigns partitions, never both.

### 🧪 Interview Q&A

**Q1:** A new Java consumer group starts on a topic with a week of data. What does it read with default settings? And with franz-go?

**Q2:** Why keep `heartbeat.interval.ms` at about a third of `session.timeout.ms`?

**Q3:** What belongs in a revoke callback, and what must never happen in a lost callback?

**Q4:** When is a consumer without a group the right choice?

> [!answer]- 📋 Answers
>
> **A1:** Java: nothing old; `latest` starts at new records only. franz-go: everything still retained, because a group without commits starts at the earliest offset.
>
> **A2:** So a couple of heartbeats can be missed (network blips) before the session expires.
>
> **A3:** Commit finished work synchronously and release resources. After a loss, another member may already own the partitions, so committing would overwrite its progress.
>
> **A4:** When one process must read all (or specific) partitions by itself, such as a debugging tool or a single-instance exporter, and rebalancing would only get in the way.

## 🔨 Hands-On Practice

1. **`latest` vs `earliest`.** With `make up` running and some orders placed:

    ```bash
    docker compose exec kafka /opt/kafka/bin/kafka-console-consumer.sh --bootstrap-server localhost:9092 \
      --topic orders --group fresh-latest --timeout-ms 6000
    docker compose exec kafka /opt/kafka/bin/kafka-console-consumer.sh --bootstrap-server localhost:9092 \
      --topic orders --group fresh-earliest --command-property auto.offset.reset=earliest --timeout-ms 6000
    ```

    ✅ The first prints `Processed a total of 0 messages`; the second processes every `OrderPaid` in the topic.

2. **A consumer outside any group.** Run `make events`, then `make lag`.

    ✅ `make events` prints every record, but no new group appears in `make lag`: it assigned itself partitions and committed nothing.

### 📋 Quick Reference

```go
kgo.NewClient(
    kgo.SeedBrokers("kafka:19092"),
    kgo.ConsumerGroup("shipping"),
    kgo.ConsumeTopics("orders"),
    kgo.FetchMaxWait(500*time.Millisecond),       // fetch.max.wait.ms
    kgo.FetchMaxBytes(50<<20),                    // fetch.max.bytes
    kgo.SessionTimeout(45*time.Second),           // session.timeout.ms
    kgo.HeartbeatInterval(3*time.Second),         // heartbeat.interval.ms
    kgo.ConsumeResetOffset(kgo.NewOffset().AtStart()), // auto.offset.reset=earliest
    kgo.Rack("eu-west-1a"),                       // client.rack
    kgo.OnPartitionsRevoked(commitOnRevoke),
)
```

### 🧠 Things to Remember

- `fetch.min.bytes` + `fetch.max.wait.ms` trade latency for fewer requests.

- Session timeout detects dead consumers; the poll/rebalance limit detects stuck ones.

- Java new groups start at `latest`; franz-go's start at the earliest offset.

- Commit in the revoke callback (or block rebalances between poll and commit); never commit lost partitions.

- Cancel the context and `Close()` to leave the group cleanly.

### 💡 Pro Tips

- **Set the start offset explicitly** → the Java and franz-go defaults differ, and the difference only shows up the day a new group is created.

- **Raise `fetch.min.bytes` for many low-traffic consumers** → fewer empty fetches load the brokers less.

- **Use rack-aware fetching in multi-zone clusters** → cross-zone traffic is often the biggest Kafka bill item in the cloud.
