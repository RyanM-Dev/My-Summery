Understand the idea

SQL has a declarative surface: a query states the desired relation and PostgreSQL chooses how to execute it. Learn the language categories and how statements are composed. Think about result shape and semantics first, then inspect the execution plan when performance matters. Start with the result the application needs or the rule the database must protect. Choose a PostgreSQL feature that expresses that requirement, then identify evidence that would show it is correct.

Worked example

SELECT customer_id, count(*) AS order_count
FROM orders
GROUP BY customer_id;

Describe the result you need; the planner selects an execution strategy. Do not assume physical row order without `ORDER BY`.

Practice

Describe a report in terms of its expected rows and columns. Write a query, then inspect the plan without forcing a scan type.

Do not infer performance from a tiny table or correctness from one happy-path row. Choose evidence that exposes the behavior you are learning.
