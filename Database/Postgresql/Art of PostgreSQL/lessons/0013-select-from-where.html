Understand the idea

Understand the core query shape: choose source relations, combine rows, filter them, and project output columns or computed expressions. A join changes row cardinality; inspect keys and expected multiplicity before adding aggregates. Start with the result the application needs or the rule the database must protect. Choose a PostgreSQL feature that expresses that requirement, then identify evidence that would show it is correct.

Worked example

SELECT c.name, o.id, o.total * 1.08 AS total_with_tax
FROM customers AS c
JOIN orders AS o ON o.customer_id = c.id
WHERE o.created_at >= DATE '2026-01-01';

Projection, source relations, join condition, and row filter each contribute to the result. Validate the join's expected row multiplicity.

Practice

Join customers to orders. Predict how many rows each customer can produce, then verify the join cardinality.

Do not infer performance from a tiny table or correctness from one happy-path row. Choose evidence that exposes the behavior you are learning.
