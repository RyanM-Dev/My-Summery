Short answer: you usually don't need to move them. A shared library step runs inside the pipeline that calls it, so it sees the same env. If the Jenkinsfile sets REGISTRY, IMAGE_NAME and
IMAGE_TAG in its environment {} block, your library code can read them two ways:

- In Groovy: env.REGISTRY
- In a single-quoted sh '...': $REGISTRY, because the shell reads it from the en

Your current code will work as it is. There are three common ways to handle these values.

Option 1: Keep environment {} in the Jenkinsfile (what you have now)

// Jenkinsfile
@Library('my-shared-lib') _
pipeline {
    agent any
    environment {
        REGISTRY   = 'git.example.com'
        IMAGE_NAME = 'robot-market/jenkins'
        IMAGE_TAG  = "${env.BUILD_NUMBER}"
    }
    stages {
        stage('Build docker image') { steps { script { buildImage() } } }
        stage('Push docker image')  { steps { script { pushImage() } } }
    }
}

This is simple, but the library quietly depends on those variables existing. If a pipeline forgets to set one, it fails in a way that's hard to trace.

Option 2: Pass them as parameters (recommended)

The step says exactly what it needs, which makes the library reusable across projects:

// vars/buildImage.groovy
def call(String registry, String imageName, String tag) {
    echo "building the docker image"
    sh "docker build -t ${registry}/${imageName}:${tag} ."
}

// vars/pushImage.groovy
def call(String registry, String imageName, String tag, String credsId = 'Gitea-Docker') {
    withEnv(["REGISTRY=${registry}", "IMAGE=${registry}/${imageName}:${tag}"]) {
        withCredentials([usernamePassword(credentialsId: credsId,
                usernameVariable: 'USER', passwordVariable: 'PASS')]) {
            echo "pushing the docker image"
            sh '''
                echo "$PASS" | docker login "$REGISTRY" -u "$USER" --password-st
                docker push "$IMAGE"
            '''
        }
    }
}

Call them like this: buildImage(env.REGISTRY, env.IMAGE_NAME, env.IMAGE_TAG).

A common variant takes a Map instead, so arguments have names and can have defaults:

def call(Map cfg = [:]) {
    def registry = cfg.registry ?: 'git.example.com'
    def tag      = cfg.tag      ?: env.BUILD_NUMBER
    ...
}
// usage: buildImage(imageName: 'robot-market/jenkins')

Option 3: Set env vars from inside the library

env.REGISTRY = env.REGISTRY ?: 'git.example.com'   // set a default if not already set
// or, for just one block:
withEnv(["REGISTRY=git.example.com"]) { sh 'echo $REGISTRY' }

Quoting

- sh "...${var}..." (double quotes): Groovy fills in the value before the shell runs. Use this for Groovy variables like function parameters.
- sh '...$VAR...' (single quotes): the shell fills in the value at run time, so VAR has to be an environment variable. That's why the push step above uses withEnv.
- Never put $PASS inside double quotes. Groovy would insert the secret into the command string, and Jenkins warns about this because the password can leak into logs. Keep the credentials
  part in single quotes.

withEnv([...]) { ... } sets environment variables only for the code inside its braces. When the block ends, they're gone.

withEnv(["REGISTRY=${registry}", "IMAGE=${registry}/${imageName}:${tag}"]) {
    // here, any sh step sees $REGISTRY and $IMAGE as environment variables
}
// here, they no longer exist

Each string is "NAME=value". Since the strings use double quotes, Groovy fills in ${registry} and the other parameters first. With registry = 'git.example.com' you get REGISTRY=git.example.com, and so on.

Why push needs it and build doesn't

It comes down to the quote type each sh uses.

Build uses double quotes:
sh "docker build -t ${registry}/${imageName}:${tag} ."
Groovy replaces ${registry} and the rest before the shell runs, so the shell jus
docker build -t git.example.com/robot-market/jenkins:42 .
No environment variables are involved, so withEnv isn't needed.

Push has to use single quotes, because of the password:
sh '''
    echo "$PASS" | docker login "$REGISTRY" -u "$USER" --password-stdin
    docker push "$IMAGE"
'''
With single quotes, Groovy changes nothing. The shell gets the text with $PASS, $REGISTRY and $IMAGE still in it and looks them up as environment variables when it runs.

- $PASS and $USER exist because withCredentials sets them as environment variables.
- registry, imageName and tag are only Groovy function parameters. The shell can, $REGISTRY and $IMAGE would be empty.

So withEnv copies the Groovy parameters into environment variables, which lets the single-quoted script use them.

Why not just use double quotes for push too?

You could write:
sh "echo \$PASS | docker login ${registry} -u \$USER --password-stdin"
The \$ stops Groovy from filling in PASS, so the shell still reads it from the environment, and this works. But mixing ${...} (filled in by Groovy) with \$... (filled in by the shell) in one
string is easy to get wrong. If you forget a backslash, Groovy puts the real paswhich can leak it into logs. The withEnv plus single quotes approach keeps itsimple: everything in the script is filled in by the shell, and the secret never passes through Groovy.

Rule of thumb: for a script that uses credentials, use single quotes and pass any other values in through withEnv. For a script without secrets, double quotes with ${...} are fine.)

## Notes: Docker class + `vars/` wrappers (from a later chat)

### Who expands `$`: Groovy or the shell?
The instructor's `${script.PASS}` tip is not really about "`$` as a character". It is about **which interpreter expands the `$`**.

1. **Groovy** processes the string first. In `"..."` or `"""..."""`, `$x` / `${expr}` is replaced by Groovy before Jenkins runs anything.
2. **The shell** (`sh`) gets the finished text. In `'...'` or `'''...'''`, Groovy changes nothing, so the shell expands `$VAR` itself from the environment.

| Quote | Who expands `$` | `$x` must be... |
|---|---|---|
| `"..."` / `"""..."""` | Groovy | a Groovy variable / parameter |
| `'...'` / `'''...'''` | the shell | an environment variable |

### Why `${script.PASS}` inside a class
- In `vars/*.groovy` the code runs as part of the pipeline script, so Groovy can see pipeline variables directly.
- In a class (`com.example.Docker`) it can't. `"echo $PASS"` makes Groovy look for a `PASS` variable inside the class and throws `MissingPropertyException`.
- `${script.PASS}` asks the pipeline object (passed into the constructor) for the value.
- Rule: in a class, reach pipeline things through `script.` (`script.sh`, `script.echo`, `script.withCredentials`, `script.PASS`), and that only works in an interpolating (double-quoted) string.

### Bug: mixing both styles
```groovy
script.sh '''
  echo '${script.PASS}' | docker login ...   // WRONG
'''
```
`'''` never interpolates, so the shell receives the literal text `${script.PASS}` and fails. Function parameters such as `REGISTRY` are Groovy variables, not env vars, so the shell can't see them either.

### Secrets: don't interpolate them in Groovy
Putting `${script.PASS}` into a `"""` string puts the password in a Groovy string. Jenkins warns about this ("Groovy String interpolation of secrets") and it can leak into logs.

Safe pattern: keep the credentials part in `'''` (shell reads `$PASS` / `$USER` from the env set by `withCredentials`) and pass the other values with `withEnv`.

### `withEnv` direction
```groovy
script.withEnv(["REGISTRY=${REGISTRY}"]) { ... }
//               ^ env var     ^ Groovy argument
```
It copies Groovy values **into** env vars (only inside the braces) so a single-quoted shell script can see them. It is the bridge between Groovy variables and the shell.

Alternative: define `REGISTRY`, `IMAGE_NAME`, `IMAGE_TAG` in the Jenkinsfile `environment {}` block, so the shell already sees them and no arguments / `withEnv` are needed.

| Approach | Pros | Cons |
|---|---|---|
| Arguments + `withEnv` | self-contained, reusable in any pipeline | slightly more code |
| Rely on pipeline env vars | simplest code | hidden contract: breaks silently if names differ |

### Final `Docker` class
```groovy
#!/usr/bin/env groovy
package com.example

class Docker implements Serializable {
  def script
  Docker(script) { this.script = script }

  def buildDockerImage(String registry, String imageName, String imageTag) {
    script.echo "building the docker image"
    script.sh "docker build -t ${registry}/${imageName}:${imageTag} ."   // double quotes: Groovy fills values, no secrets
  }

  def pushDockerImage(String registry, String imageName, String imageTag) {
    script.echo "pushing the docker image"
    script.withEnv(["REGISTRY=${registry}", "IMAGE_NAME=${imageName}", "IMAGE_TAG=${imageTag}"]) {
      script.withCredentials([script.usernamePassword(
          credentialsId: 'Gitea-Docker',
          usernameVariable: 'USER',
          passwordVariable: 'PASS')]) {
        script.sh '''
          echo "$PASS" | docker login "$REGISTRY" -u "$USER" --password-stdin
          docker push "$REGISTRY/$IMAGE_NAME:$IMAGE_TAG"
        '''   // single quotes: the shell reads everything from env vars
      }
    }
  }
}
```

### Good practice: thin `vars/` wrappers, logic in the class
Keep the logic in `src/` (class) and make each `vars/` file a thin wrapper, so there is no duplicated code.

```groovy
// vars/buildimage.groovy
import com.example.Docker
def call(String registry, String imageName, String imageTag) {
    new Docker(this).buildDockerImage(registry, imageName, imageTag)
}

// vars/pushimage.groovy
import com.example.Docker
def call(String registry, String imageName, String imageTag) {
    new Docker(this).pushDockerImage(registry, imageName, imageTag)
}
```
- `this` inside a `vars/` file is the pipeline script context, so it is the `script` the class uses for `sh`, `echo`, `withCredentials`.
- The Jenkinsfile stays short: `buildimage(env.REGISTRY, env.IMAGE_NAME, env.IMAGE_TAG)`.

### Folder structure gotcha
`package com.example` maps to **nested folders**:
```
Groovy-script/
├── src/com/example/Docker.groovy     <- NOT src/com.example/ (one folder with a dot)
└── vars/
    ├── buildJar.groovy
    ├── buildimage.groovy
    └── pushimage.groovy
```
A folder literally named `com.example` makes `import com.example.Docker` fail to resolve.

### Other good practices
- Name Groovy parameters in camelCase (`registry`, `imageName`, `imageTag`). UPPERCASE looks like an env var and causes confusion.
- Make the credentials ID a parameter with a default (`String credsId = 'Gitea-Docker'`) so other pipelines can reuse the step.
- Pin the library version: `@Library('jenkins-shared-lib@main')_` or a tag. Use a branch while testing, a tag for stable use.
- Classes that hold the pipeline `script` must `implements Serializable` (Jenkins can pause and resume pipelines).
- The `post { always { sh 'docker logout ${REGISTRY}' ... } }` cleanup is fine in the Jenkinsfile: single quotes, so the shell reads the pipeline `environment`.

## Loading a shared library without global config (inside the Jenkinsfile)

Instead of registering the library under **Manage Jenkins > System > Global Trusted Pipeline Libraries**, you can declare everything in the Jenkinsfile with the `library` step. Then each pipeline carries its own config: repo, credentials and version.

### Syntax
```groovy
library identifier: 'jenkins-shared-lib@main', retriever: modernSCM([
    $class: 'GitSCMSource',
    remote: 'https://git.example.com/robot-market/jenkins-shared-lib.git',
    credentialsId: 'Gitea-Docker'
])

pipeline {
    agent any
    ...
}
```

| Part | Meaning |
|---|---|
| `identifier: 'name@version'` | a local name for the library, plus the version after `@` |
| `@version` | branch (`@main`), tag (`@v1.0`) or commit hash |
| `retriever: modernSCM([...])` | how to fetch it |
| `$class: 'GitSCMSource'` | the source is a Git repo |
| `remote` | the library repo URL |
| `credentialsId` | Jenkins credentials used to clone it (needed for private repos) |

### Compared to `@Library`
| | `@Library('lib@ver')_` | `library identifier: ...` |
|---|---|---|
| Jenkins global config needed | yes (name, repo, creds, default version) | no |
| Where config lives | Jenkins UI | in the Jenkinsfile (versioned in Git) |
| Can be used inside the pipeline / conditionally | no (annotation, top of file only) | yes (it is a normal step) |
| Trust level | global libraries are trusted | typically sandboxed (untrusted) |

### Pros / cons
- Pros: no admin access to Jenkins needed, config is in Git and reviewable, each pipeline can pin its own version, easy to try a library branch.
- Cons: the repo URL and credentials ID are repeated in every Jenkinsfile (not DRY), sandbox restrictions can block some calls, and a typo in the config only shows up at runtime.

### Gotcha: importing classes from `src/`
`import com.example.Docker` at the top of the Jenkinsfile can fail, because the library is not loaded yet when the file is compiled. Options:
- Use the `vars/` wrappers (`buildimage(...)`, `pushimage(...)`). They work right after the `library` step. This is why the thin-wrapper pattern is good practice.
- Or keep the return value and use the class from it: `def lib = library(...)` then `lib.com.example.Docker.new(this)`.
