# 📦 Containers, Images, and Virtual Machines

## 🌐 Why Use Containers?

A **container** runs an application in an isolated environment. Its **image** packages the application and the files it needs, so you can run it without installing those dependencies directly on the server.

> 💡 **Real-World Example**
>
> Your payment application needs PostgreSQL. Installing it manually on every laptop and server means repeating installation steps and managing version differences.
>
> With Docker, each environment runs a PostgreSQL container from the chosen image. Another project can run a different version in a separate container.

| Manual deployment | Container deployment |
|---|---|
| Hand over an application artifact and installation instructions | Hand over an image and runtime configuration |
| Install dependencies separately on each server | Package dependencies into the image |
| Shared installations can cause version conflicts | Each container has its own application files |

This makes the development-to-operations handoff more repeatable. You still configure networking, storage, credentials, and a compatible container runtime. See Docker’s [container introduction](https://docs.docker.com/get-started/docker-concepts/the-basics/what-is-a-container/).

## 📦 Image vs Container

An **image** is the distributable artifact. A **container** is an instance created from it, with its own runtime configuration and writable filesystem. A stopped container still exists; it simply has no running application process.

```text
                     PostgreSQL image
                            │
                   Create two instances
                     ┌──────┴──────┐
                     ▼             ▼
                 project-a     project-b
                 container     container
                 own data      own data
```

| Image | Container |
|---|---|
| Read-only package | Runnable instance of that package |
| Can be stored in a registry | Exists on a container host |
| Can create many containers | Has its own name, state, and configuration |

Changing files inside one container does not modify its source image. See [What is an image?](https://docs.docker.com/get-started/docker-concepts/the-basics/what-is-an-image/).

### 🌍 Where Images Live

A **registry** stores images. A **repository** groups related images, and a **tag** identifies a named version within that repository.

```text
docker.io/library/postgres:16
───────── ──────────────── ──
registry      repository  tag
```

Docker Hub hosts public images; companies also use private registries for internal applications. Downloading an image is a **pull**; uploading one is a **push**. Running containers live on hosts, rather than inside the registry. See [Docker registries](https://docs.docker.com/get-started/docker-overview/#docker-registries).

## 🧱 How Image Layers Work

An image combines **filesystem layers**: changes such as adding packages or application files. Docker presents them as one filesystem and adds a writable layer for each container.

```text
┌────────────────────────────────────┐
│ Container's writable layer         │  Unique to this container
├────────────────────────────────────┤
│ Application files                  │
├────────────────────────────────────┤
│ Runtime and dependencies           │  Read-only image layers
├────────────────────────────────────┤
│ Base filesystem, e.g. Alpine       │
└────────────────────────────────────┘
             Shared Linux kernel
```

This is a conceptual stack; actual images can have many layers. A base image often contains Linux user-space files, but it does **not** supply a running kernel. Some minimal images contain only an application and essential files.

- 📦 **Layer reuse**

    - Images sharing identical layers can reuse locally stored content, reducing downloads and disk use.

- 💾 **Container changes**

    - Changes in the writable layer survive stopping the container, but disappear when that container is removed. Use persistent storage for important data.

See [Understanding image layers](https://docs.docker.com/get-started/docker-concepts/building-images/understanding-image-layers/).

💻 **Inspect an image you have downloaded:**

```bash
docker image history postgres:16
docker image inspect --format '{{json .RootFS.Layers}}' postgres:16
```

`history` shows build history; `inspect` displays the image’s filesystem-layer identifiers. `--format` selects a field instead of printing all metadata. These identifiers are not container IDs or the registry manifest digest.

## 💻 Run a PostgreSQL Container

General syntax:

```bash
docker run [OPTIONS] IMAGE [COMMAND] [ARGUMENTS...]
```

For a disposable local lesson:

```bash
docker run -d --name nana-postgres-demo \
  -e POSTGRES_PASSWORD=local-demo-only \
  postgres:16
```

- 💻 **`run`** → create and start a new container; pull the image if it is missing locally.

- 🏷️ **`--name`** → give it a name for later commands.

- 🔄 **`-d`** → run in the background and return control to your terminal.

- ⚙️ **`-e KEY=VALUE`** → pass an environment variable. This image uses `POSTGRES_PASSWORD` when initializing an empty database directory.

- 📦 **`postgres:16`** → select the PostgreSQL repository and its `16` tag.

The database runs inside the container. This command does not publish its port to your laptop. See [`docker run`](https://docs.docker.com/reference/cli/docker/container/run/) and the [PostgreSQL image instructions](https://hub.docker.com/_/postgres).

> ⚠️ The password is for a disposable exercise. Command-line credentials can appear in shell history and container metadata. Keep real credentials out of shared examples.

💻 **Check its state and startup messages:**

```bash
docker ps
docker logs nana-postgres-demo
```

`ps` lists running containers; look for the name and `STATUS`. `logs` shows the application’s output; PostgreSQL should eventually report that it is ready to accept connections.

## 🖥️ Containers vs Virtual Machines

The **kernel** manages hardware and operating-system resources. **User space** contains programs, libraries, and tools. Linux distributions combine a Linux kernel with different user-space packages and defaults.

A Linux container shares the kernel of its container host. A **virtual machine (VM)** runs a guest operating system with its own kernel, using virtual hardware supplied by a hypervisor.

```text
Linux containers                 Virtual machines
┌──────────┬──────────┐          ┌──────────┬──────────┐
│ App A    │ App B    │          │ App A    │ App B    │
│ Libraries│ Libraries│          │ Guest OS │ Guest OS │
├──────────┴──────────┤          │ + kernel │ + kernel │
│ Shared Linux kernel│          ├──────────┴──────────┤
├────────────────────┤          │ Hypervisor         │
│ Hardware           │          ├────────────────────┤
└────────────────────┘          │ Hardware           │
                                └────────────────────┘
```

| Question | Container | VM |
|---|---|---|
| Separate kernel? | Shares the container host’s kernel | Has a guest kernel |
| Startup overhead? | Usually lower; starts application processes | Includes guest OS startup |
| Typical size? | Often smaller, depending on packaged files | Often larger, including a guest OS |
| Isolation boundary? | OS-level isolation | Virtual hardware and guest OS |

Containers and VMs often work together: a VM can host many containers. Avoid memorizing fixed sizes or startup times; the application and environment affect both. See Docker’s [container and VM comparison](https://docs.docker.com/get-started/docker-concepts/the-basics/what-is-a-container/#containers-versus-virtual-machines-vms).

### 🐧 How Docker Desktop Runs Linux Containers

Linux images need a Linux kernel. Docker Desktop supplies a Linux VM on macOS and uses a Linux backend such as WSL 2 on Windows. Docker Desktop for Linux also uses a VM; native Docker Engine on Linux can use the host kernel directly.

```text
macOS / Windows → Linux VM → Linux kernel → Linux containers
```

Windows containers also exist and require a compatible Windows environment. An image must match the target operating system and CPU architecture, or use a supported emulation setup. See [Desktop VM options](https://docs.docker.com/desktop/features/vmm/) and [Windows installation](https://docs.docker.com/desktop/setup/install/windows-install/).

### 🧪 Interview Q&A

**Q1:** What do you upload to a registry: an image or a running container?

**Q2:** Why can two projects use different PostgreSQL versions on the same host?

**Q3:** Does an Alpine-based image boot its own Linux kernel?

**Q4:** If you stop and restart a container, do its filesystem changes disappear?

> [!answer]- 📋 Answers
>
> **A1:** An image. The deployment host creates containers from it.
>
> **A2:** Each container has separate application files and dependencies. Shared host resources such as published ports still need coordination.
>
> **A3:** No. It supplies user-space files and uses the container host’s Linux kernel.
>
> **A4:** No. Stopping preserves the container. Removing it deletes its writable layer; persistent storage has a separate lifecycle.

## 🔨 Hands-On Practice

Use a local Docker installation and disposable data. The first run may download the image.

1. 📦 **Run the PostgreSQL example above.**

   Check `docker ps` and its logs. If the chosen name already exists, choose a new name throughout the exercise.

2. 🔎 **Compare image and container state.**

   ```bash
   docker image ls postgres
   docker stop nana-postgres-demo
   docker ps -a --filter name=nana-postgres-demo
   ```

   `image ls` lists the package. `stop` requests shutdown; `ps -a` includes stopped containers, and `--filter` narrows the list.

   ✅ The image remains available and the container appears as exited.

3. 🧹 **Remove only the disposable container and its anonymous volume.**

   ```bash
   docker rm -v nana-postgres-demo
   ```

   `rm` removes the stopped container; `-v` also removes its attached anonymous volumes, including this demo’s database storage. This deletes the demo data; the image remains available. See [`docker rm`](https://docs.docker.com/reference/cli/docker/container/rm/).

### 🧠 Things to Remember

- Images package files; containers run processes using those files.

- Linux containers share a kernel and do not boot a full guest OS.

- Identical image layers can be reused; each container has its own writable layer.

- Application data needs persistent storage when containers are replaced.

### 💡 Pro Tips

- Choose explicit image versions. Tags can move; use a verified digest when you need the exact same image content.

- Run one container per service so you can update and restart services independently.

- Check logs before assuming a container shown in `docker ps` is ready to serve requests.
