### 📖 Chapter Summary

Chapter 3 of *Learning Go* (Bodner) introduces Go’s composite types: arrays (rigid and rarely used directly), slices (the workhorse), maps, and structs. It explains the critical built-in functions (`len`, `append`, `make`, `copy`), the difference between nil and empty collections, capacity vs length, slice expressions, and how Go handles strings/runes/bytes. The chapter stresses that slices are references to an underlying array and that Go is a call-by-value language — facts that explain many surprising behaviors.

*100 Go Mistakes* (Harsanyi) devotes a large portion of its Data Types chapter to exactly these topics, cataloging common errors: misunderstanding slice length/capacity (#20), inefficient initialization (#21), nil vs empty slices (#22), improper empty checks (#23), incorrect copying (#24), append side effects (#25), memory leaks (#26), map initialization and leaks (#27–#28), and incorrect value comparison (#29).

This chapter forms the foundation for almost everything that follows in Go.

## Part 1: Arrays — Too Rigid to Use Directly

### 📌 Concepts Explained

- The length of an array is **part of its type**: `[3]int` ≠ `[4]int`.
- You cannot use a variable for the size.
- You generally cannot assign or convert between arrays of different lengths.
- Arrays are the backing store for slices.

### 🔧 Bodner — When Arrays Are Appropriate

Use arrays only when you know the exact size at compile time (e.g., cryptographic hash sizes returned by the standard library).

```go
// Bodner example
var x [3]int                  // all zeros
var y = [3]int{10, 20, 30}
var z = [...]int{10, 20, 30}  // compiler counts

// Multidimensional (array of arrays)
var matrix [2][3]int
```

Comparison works only for arrays of identical type:
```go
fmt.Println(x == y) // true if same length + values
```

### 🔧 Why Arrays Feel Limited (and That’s Intentional)

Because size is part of the type, you cannot write a single function that accepts arrays of any length. This limitation is the main reason slices exist.

## Part 2: Slices — The Heart of Go Data Structures

### 📌 Concepts Explained

A slice is a **descriptor** containing:
- Pointer to underlying array
- Length
- Capacity

`len(s)` returns current length. `cap(s)` returns size of backing array.

### 🔧 Bodner — Declaring and Using Slices

```go
var s []int                 // nil slice (zero value)
s = []int{1, 2, 3}          // slice literal
s = make([]int, 5)          // len=5, cap=5, all zero
s = make([]int, 5, 10)      // len=5, cap=10
```

**Important**: A nil slice is valid for `len`, `cap`, `append`, and `for range`.

### 🔧 append — The Most Important Slice Operation

```go
// Must assign the result — Go is call-by-value
s = append(s, 4)
s = append(s, 5, 6, 7)
other := []int{10, 20}
s = append(s, other...)     // spread
```

Forgetting the assignment is a compile-time error in many cases, but the result must still be captured because append may return a new slice header.

### 🔧 Capacity, Growth, and Leaks (Bodner + Harsanyi)

When `append` runs out of capacity it allocates a new, larger backing array (usually ~2×) and copies elements.

Harsanyi #20, #21, #26 cover:
- Not understanding that `cap` can be larger than `len`
- Inefficient repeated small appends without pre-allocation
- Memory leaks when large backing arrays are kept alive by small slices

**Best practice**:
```go
// Pre-allocate when you know the size
result := make([]T, 0, expectedSize)
for ... {
    result = append(result, val)
}
```

### 🧪 Interview Q&A

**Q1:** What is the difference between `len` and `cap` for a slice?

**Q2:** (Real-world) Why must the return value of `append` always be assigned back to a variable?

**Q3:** How do you safely create a slice with a known capacity to avoid repeated allocations?

> [!success]- 📋 Answers — Part 2
> **A1:** `len(s)` is the number of elements currently accessible. `cap(s)` is the number of elements in the underlying array (maximum len before reallocation on append).
>
> **A2:** `append` receives a copy of the slice header. If it reallocates, it returns a new header. Without assignment you lose the new data/length.
>
> **A3:** `s := make([]T, 0, expectedLen)`. Then repeated `append` will usually not reallocate until capacity is reached.

## Part 3: Slicing Slices, copy, and Common Pitfalls

### 📌 Concepts Explained

Slice expressions create new slice headers over the same backing array:
```go
s := []int{0, 1, 2, 3, 4, 5}
t := s[1:4]        // [1,2,3], shares backing array
```

Changes to `t` are visible in `s` (and vice versa) within the overlapping region.

### 🔧 copy

```go
dst := make([]int, len(src))
copy(dst, src)     // correct order: destination first
```

Harsanyi #24 shows many people get the order or length wrong.

### 🔧 Harsanyi Slice Mistakes to Avoid

- #22: Treating `nil` and empty slice as the same (they are different for JSON, some APIs, and `append` behavior in edge cases).
- #23: Incorrect “is empty” checks (`len(s) == 0` is correct and works for both nil and empty).
- #25: Append side effects — appending to a sliced subslice can overwrite data in the original slice because they share the backing array.
- #26: Leaking capacity — keeping a small slice header that points into a huge backing array.

## Part 4: Strings, Runes, and Bytes

### 📌 Concepts Explained

- `string` is an immutable sequence of bytes (conventionally UTF-8).
- `rune` = Unicode code point (`int32`).
- Iterating with `range` gives byte index + rune.
- Converting between `string` and `[]byte` or `[]rune` copies data.

Bodner gives a preview here (deeper treatment later).

```go
s := "hello, 世界"
for i, r := range s {
    fmt.Printf("%d %c\n", i, r)
}
```

Harsanyi covers related string mistakes in Ch.5 (runes, iteration, trim, concatenation).

## Part 5: Maps

### 📌 Concepts Explained

Maps are unordered collections of key/value pairs. The zero value is `nil`.

- You cannot compare maps with `==` (except to `nil`).
- Use comma-ok idiom for safe lookup.
- `delete(m, key)` removes a key.
- Since Go 1.21: `clear(m)` empties a map.

### 🔧 Bodner — Map Basics

```go
m := map[string]int{"a": 1}
v, ok := m["a"]          // comma-ok
if ok { ... }

m["b"] = 2
delete(m, "a")

for k, v := range m { ... }
```

### 🔧 Harsanyi Map Mistakes

- #27: Inefficient map initialization (not pre-allocating with `make` when size is known).
- #28: Map memory leaks (similar capacity issues as slices when holding references).
- #29: Incorrect assumptions when comparing map values or expecting order.

## Part 6: Structs

### 📌 Concepts Explained

Structs are composite types that group fields.

- Can be compared with `==` if all fields are comparable.
- Anonymous structs are useful for one-off data or tests.
- Structs are value types (copied on assignment/pass unless you use a pointer).

### 🔧 Bodner Examples

```go
type Person struct {
    Name string
    Age  int
}

p := Person{Name: "Alice", Age: 30}
p2 := p                    // copy
```

Anonymous:
```go
tmp := struct {
    X int
    Y string
}{X: 1, Y: "hi"}
```

### 🧪 Interview Q&A — Master

**Q1:** Why are arrays rarely used directly in Go?

**Q2:** What happens if you forget to assign the result of `append`?

**Q3:** Explain the difference between a nil slice and an empty slice. When does it matter?

**Q4:** Why can `append` to a subslice corrupt data in the original slice?

**Q5:** Show the comma-ok idiom for a map. What does the `ok` value mean?

**Q6:** When should you pre-allocate a slice with `make(..., 0, size)`?

**Q7:** Can you compare two slices with `==`? What are the modern alternatives?

**Q8:** What is the relationship between `string`, `[]byte`, and `[]rune`?

**Q9:** (Real-world) What is the difference between a nil map and an empty map in Go? What happens if you try to write to each?

**Q10:** (Real-world) Given `s := []int{1,2,3}; t := s[1:2]; t = append(t, 99);` — what are the values of s and t after? Why?

> [!success]- 📋 Answers — Part 8
> **A1:** The length is part of the array’s type. `[3]int` is a different type from `[4]int`. You cannot write generic code over different array sizes. Slices remove this limitation.
>
> **A2:** The append may allocate a new backing array and return a new slice header. Without assigning the result, your variable still points at the old (possibly full) header and you lose the appended data.
>
> **A3:** `var s []int` is `nil` (len=0, cap=0, no backing array). `[]int{}` or `make([]int, 0)` is non-nil but empty. Some APIs (JSON marshaling, database drivers) treat them differently. `len(s) == 0` works for both.
>
> **A4:** A subslice shares the same backing array. Appending to it can overwrite elements beyond its current length but still inside the original slice’s capacity.
>
> **A5:** `v, ok := m[key]`. `ok` is true if the key existed. If the key does not exist, `v` is the zero value for the value type.
>
> **A6:** When you know (or can estimate) the final size. This avoids multiple reallocations during growth.
>
> **A7:** No (except against `nil`). Use `slices.Equal` (or `slices.EqualFunc`) from the standard library since Go 1.21.
>
> **A8:** `string` is immutable bytes. `[]byte(s)` and `string(b)` copy data. `[]rune` works at the Unicode code-point level. Range over string gives runes; indexing a string gives bytes.
>
> **A9:** A nil map (`var m map[string]int`) cannot be written to (panic on assignment). An empty map (`make(map[string]int)` or `map[string]int{}`) can be read/written immediately. Reading from either returns the zero value + false for comma-ok. Many APIs distinguish them (e.g. JSON).
>
> **A10:** s becomes [1,2,99,3] or similar depending on capacity — t = append to a subslice that shares backing array can mutate s beyond t's len. This is a classic gotcha. To avoid, copy first: `t := slices.Clone(s[1:2])`.
