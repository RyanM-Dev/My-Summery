### 📖 Chapter Summary

Chapter 5 of *Learning Go* (Bodner) covers Go’s function model: declaring and calling functions, variadic parameters, multiple return values (especially the `(T, error)` idiom), named result parameters, functions as first-class values, anonymous functions, closures, passing and returning functions, and `defer` for cleanup. It reinforces that Go is **call-by-value** — including the critical detail that slices and maps are small descriptors pointing at shared backing storage.

*100 Go Mistakes* (Harsanyi) surfaces practical traps around methods and functions: receiver choice preview (#42), named result parameters (#43–#44), nil receiver panics (#45), passing filenames instead of open resources (#46), `defer` argument evaluation (#47), and `defer` inside loops (#35).
*Go in Practice* (2nd ed., Ch.3) applies functions to production structs: methods with receivers `(a Animal) speak()`, constructor functions like `NewCat()`, and functions stored inside struct fields — the bridge from “functions” to “methods and types.”

This chapter is where error handling, resource cleanup, and higher-order patterns become idiomatic Go.

## Part 1: Declaring, Calling, and Variadic Functions

### 📌 Concepts Explained

- Functions are declared with `func`, a name (optional for anonymous), parameters, optional return types, and a body.
- Go has no overloading — each function name is unique in its package.
- **Variadic** parameters (`nums ...int`) collect zero or more trailing arguments into a slice inside the function.
- Functions are **first-class**: they have a type like any other value.

### 🔧 Bodner — Basic Declaration and Variadic

```go
func sum(nums ...int) int { /* nums is []int inside */ }
fmt.Println(sum(1, 2, 3))
fmt.Println(sum(more...)) // spread slice into variadic call
```

### 🔧 Bodner — Calculator `opMap` (Functions as Values Preview)

Bodner’s calculator dispatches operations via a map of functions — a pattern you will see in plugins, middleware, and CLI subcommands:

```go
// Learning Go (Bodner) — opMap dispatch
var opMap = map[string]func(int, int) int{
    "+": func(a, b int) int { return a + b },
    "-": func(a, b int) int { return a - b },
    "*": func(a, b int) int { return a * b },
    "/": func(a, b int) int { return a / b },
}

func calculate(op string, a, b int) (int, error) {
    fn, ok := opMap[op]
    if !ok {
        return 0, fmt.Errorf("unknown op: %s", op)
    }
    return fn(a, b), nil
}
```

## Part 2: Multiple Return Values and the Error Idiom

### 📌 Concepts Explained

- Go functions can return multiple values — most commonly `(result, error)`.
- Callers **must** handle or explicitly ignore each return with `_`.
- Errors are values, not exceptions. Check `err != nil` immediately.
- This pattern composes with `if err := fn(); err != nil { ... }` for tight scope.

### 🔧 Bodner — Multiple Returns

```go
// Learning Go (Bodner) — idiomatic (T, error)
func divide(a, b float64) (float64, error) {
    if b == 0 {
        return 0, fmt.Errorf("divide by zero")
    }
    return a / b, nil
}
```

### 🔧 Harsanyi — Ignoring Returns Is a Mistake

```go
// Common mistake — silent failure
divide(10, 0) // compile error in Go: must use return values

// Still a mistake — explicit ignore without comment
_ = someOperation() // OK syntactically; dangerous if error matters

// 2026 senior standard — handle or document why ignored
if err := db.Ping(); err != nil {
    return fmt.Errorf("ping db: %w", err)
}
```

### 🧪 Interview Q&A

**Q1:** What is the idiomatic way to return an error from a function?

**Q2:** What does `_` do when receiving multiple return values?

**Q3:** (Real-world) Why is `if err := fn(); err != nil` preferred over assigning `err` in an outer scope?

> [!success]- 📋 Answers — Part 2
> **A1:** Return `(zeroValue, err)` on failure and `(result, nil)` on success. Use `fmt.Errorf` or custom error types; wrap with `%w` when appropriate (Ch.9).
>
> **A2:** `_` is the blank identifier — it discards a value deliberately. Required when you must receive but not use a return (e.g. `_, err := fmt.Fprintf(...)`).
>
> **A3:** `err` is scoped to the `if` block, preventing accidental reuse/shadowing of a stale `err` variable and keeping error handling local to the operation.

## Part 3: Named Return Values — Power and Pitfalls

### 📌 Concepts Explained

- **Named result parameters** appear in the function signature: `func f() (result int, err error)`.
- They are initialized to their type’s zero value and act like variables in the function body.
- A **naked return** (`return` with no values) returns the current values of named results — Bodner and Harsanyi both warn against overusing this.
- Named returns help documentation and short functions; they become dangerous with defer/recover side effects.

### 🔧 Bodner — Named Returns (Good Use)

```go
// Learning Go (Bodner) — named returns clarify API
func splitHostPort(hostport string) (host, port string, err error) {
    host, port, err = net.SplitHostPort(hostport)
    if err != nil {
        return // naked return OK here — short, obvious
    }
    if host == "" {
        host = "localhost"
    }
    return host, port, nil
}
```

### 🔧 Harsanyi #43–#44 — Named Return Side Effects

```go
// Common mistake (Harsanyi #44) — defer observes/mutates named err
func divide(a, b int) (result int, err error) {
    defer func() { if err != nil { result = 0 } }()
    if b == 0 { err = fmt.Errorf("divide by zero"); return }
    result = a / b; return
}

// Better — unnamed results + explicit return
func divide(a, b int) (int, error) {
    if b == 0 { return 0, fmt.Errorf("divide by zero") }
    return a / b, nil
}
```

**Harsanyi #43:** Named results change how `return` and `defer` interact — not just documentation.

## Part 4: Functions as Values, Anonymous Functions, and Closures

### 📌 Concepts Explained

- Function types are explicit: `type Op func(int, int) int`.
- Functions can be assigned to variables, stored in structs/maps, passed as arguments, and returned from other functions.
- **Anonymous functions** are declared inline without a name.
- A **closure** is a function that references variables from an enclosing scope — it captures those variables for later use.

### 🔧 Bodner — Passing and Returning Functions

```go
// Learning Go (Bodner) — higher-order function
func makeMultiplier(factor int) func(int) int {
    return func(x int) int {
        return x * factor // closure captures factor
    }
}

double := makeMultiplier(2)
fmt.Println(double(5)) // 10
```

### 🔧 Closure — `sort.Slice` Comparator (Bodner Pattern)

```go
type Person struct {
    Name string
    Age  int
}

people := []Person{{"Alice", 30}, {"Bob", 25}}

// Closure captures people slice for comparison
sort.Slice(people, func(i, j int) bool {
    return people[i].Age < people[j].Age
})
```

### 🔧 Go in Practice — Functions Inside Structs + Constructor

GiP Ch.3 stores behavior on structs via methods and constructor factories:

```go
// Go in Practice (2nd ed.) Ch.3 — constructor + method receiver
type Animal struct { Name string; Age int }

func NewCat(name string, age int) *Animal {
    return &Animal{Name: name, Age: age}
}

func (a Animal) speak() string { return "meow" }
```

### 🔧 Harsanyi #42 / #45 — Receiver Preview

```go
func (a Animal) SetAge(age int)  { a.Age = age }  // #42: copy — no mutation
func (a *Animal) SetAge(age int) { a.Age = age }  // pointer — mutates caller's animal
// #45: nil pointer receiver panics if method dereferences a
```

## Part 5: defer — Deep Dive

### 📌 Concepts Explained

- `defer` schedules a function call to run when the surrounding function **returns** (after results are set, before control passes to caller).
- Deferred calls run in **LIFO** (last-in, first-out) order — like a stack.
- **Arguments to the deferred function are evaluated immediately** at the `defer` statement, not at execution time (Harsanyi #47).
- Primary uses: close files, unlock mutexes, rollback transactions, recover from panic (Ch.9).

### 🔧 Bodner — defer File Close

```go
// Learning Go (Bodner) — idiomatic file cleanup
func readConfig(path string) ([]byte, error) {
    f, err := os.Open(path)
    if err != nil {
        return nil, err
    }
    defer f.Close() // runs when readConfig returns

    return io.ReadAll(f)
}
```

### 🔧 Harsanyi #47 / #35 — defer Gotchas

```go
i := 0
defer fmt.Println(i)              // #47: prints 0 — arg evaluated at defer line
defer func() { fmt.Println(i) }() // prints 1 — closure reads i at execution

// #35 — defer in loop stacks until outer function returns
for _, path := range paths {
    f, _ := os.Open(path)
    defer f.Close() // BAD: leaks FDs until processFiles exits
}
// Fix: per-file helper with its own defer, or explicit Close() in loop
```

### 🔧 Transaction defer Pattern (Production)

Database and RPC code often uses defer for rollback unless committed:

```go
tx, err := db.BeginTx(ctx, nil)
if err != nil { return err }
defer tx.Rollback() // no-op after successful Commit
// ... debit/credit ...
return tx.Commit()
```

## Part 6: Call-by-Value and Pointer-Backed Types

### 📌 Concepts Explained

- Go is **always call-by-value**. The callee receives a copy of each argument.
- For slices, maps, channels, and pointers, the copy is a **descriptor** (header or pointer) — mutations through that copy are visible to the caller.
- This explains Ch.3 append behavior and why you must return updated slice headers.
- Passing a **filename string** is not the same as passing an open `*os.File` (Harsanyi #46).

### 🔧 Bodner — Call-by-Value Implications

```go
func addToSlice(s []int, v int) {
    s = append(s, v) // may not visible to caller without return assignment
}

func mutateMap(m map[string]int) {
    m["key"] = 42 // visible — map header copied, same backing hash
}

func main() {
    nums := []int{1, 2}
    addToSlice(nums, 3) // nums unchanged (len still 2) unless reassigned from return

    data := map[string]int{}
    mutateMap(data) // data now has "key"
}
```

### 🔧 Harsanyi #46 — Filename vs Open File

Pass `io.Reader` or `*os.File` when the caller should own lifecycle — easier to test with `bytes.NewReader` than passing a filename string the callee must open.

## Part 8: Senior Recommendations + Master Q&A

### 📊 Diagram — defer Stack (LIFO)

```
func example() {
    defer fmt.Println("1")  // pushed third → runs first
    defer fmt.Println("2")  // pushed second → runs second
    defer fmt.Println("3")  // pushed first  → runs last
    fmt.Println("body")
}
// Output: body → 3 → 2 → 1
```

### 🧪 Interview Q&A — Master

**Q1:** What does it mean that Go is call-by-value? How does that affect slices?

**Q2:** Explain variadic parameters and how to spread a slice into a variadic call.

**Q3:** What is the `(T, error)` idiom? When do you use `_`?

**Q4:** What are named return values and naked returns? Why avoid them in complex functions?

**Q5:** How does the calculator `opMap` pattern work? When is a map of functions appropriate?

**Q6:** What is a closure? Give an example with `sort.Slice`.

**Q7:** How does `defer` work? When are arguments evaluated?

**Q8:** Why should you avoid `defer` in a loop? What is the fix?

**Q9:** (Real-world) Value vs pointer receiver — when does each apply? What happens with a nil pointer receiver (#42, #45)?

> [!success]- 📋 Answers — Part 8
> **A1:** Callees get copies of arguments. For slices, the copy is the header (ptr/len/cap). Mutations through shared backing storage are visible; reallocation requires returning the new header.
>
> **A2:** `...T` collects trailing args into `[]T`. Spread with `fn(slice...)`. The slice must be the same element type as the variadic parameter.
>
> **A3:** Return a result and an error; check `err != nil` before using the result. Use `_` to explicitly discard a return you do not need (e.g. `_, err := fmt.Scan(...)`).
>
> **A4:** Named results are variables in the signature; naked `return` returns their current values. Avoid in long functions or with defer/recover — side effects on named `err` confuse readers (#43–#44).
>
> **A5:** `map[string]func(...)` maps operation names to implementations. Good for small finite dispatch (calculators, simple plugins). For larger APIs prefer interfaces.
>
> **A6:** A function referencing outer variables. `sort.Slice` takes `less(i,j)`; closure reads `people[i]` and `people[j]` to define order without a separate named compare function.
>
> **A7:** Schedules a call at function exit; multiple defers run LIFO. Arguments are evaluated at the `defer` line (#47), not at exit — wrap in `func(){...}()` for late binding.
>
> **A8:** Defers stack until the outer function returns, delaying cleanup (#35). Fix: per-iteration helper with its own defer, or explicit `Close()` in the loop body. Transaction pattern: `defer tx.Rollback()` is safe — no-op after `Commit()`.
>
> **A9:** Value receiver for small immutable types; pointer for mutation or large structs (#42). Nil pointer receiver panics if the method dereferences `a` (#45); guard with `if a == nil` when needed.
